Persistent MXFP8 attention scheduling experiment
2026-11-13 UTC

Outcome
Cost-balanced static assignment improves the prepared MXFP8 core. No atomic work queue is used.
It is opt-in, with a reusable schedule built from known CPU sequence lengths.
All arithmetic, precision, async waits and output ownership stay the same.
The previous static assignment leaves long-KV workgroups with very different amounts of work.

Why persistence was insufficient
The old kernel gives each CTA a fixed grid-stride list of (query tile, head) work items.
Item count is similar across CTAs, but KV lengths differ. Some CUs retire their last CTA early.
For control_long_0, the cost model gives mean109.22 outer iterations/CTA and max260.
Global capacitated longest-job-first assignment lowers the modeled max to132.
Each outer iteration represents two128-key tiles. These are work estimates, not timing predictions.
An XCD-local balanced assignment helps, but global balancing consistently wins on long KV.
Inserting an identity indirection alone slows the long cases: the order change supplies the gain.

Current inefficiencies after balancing
1. Padding: control_long_0 query padding multiplies main matrix work by2.46294x;
   key padding adds1.01812x, for2.50757x overall. About60% of issued main matrix arithmetic
   therefore acts on padding. It is a work count, not a60% runtime saving opportunity.
   Small-query tiles tested so far lose because they increase K/V visits and reduce intensity.
   BM64 also uses only two warps per CTA with a similar K/V LDS allocation, limiting latency hiding.
2. Memory: at BM128, main matrix arithmetic / requested K/V byte is248.24FLOP/byte.
   This is below the board machine balance (~677.5FLOP/byte at dense4.614PF/s and6.810TB/s).
   A pure matrix-compute ceiling therefore cannot describe this streaming workload.
3. Softmax, MXFP8 conversion and scale bookkeeping impose substantial vector issue work.
   Row-sum MFMA adds6.25% arithmetic beyond QK/PV. These costs remain after work balancing.
4. Two CTAs/CU, dependent shared-memory reads, synchronization and remaining scratch spills
   constrain latency hiding. ATT still contains waits; their sum is not a runtime breakdown.
5. Full BF16 input still needs K/V quantization and transpose. This report measures prepared operands.
   No new full-BF16 end-to-end win over AITER is claimed.

New same-GPU read-only calibration reads4GiB and writes only one32-bit reduction result per block.
Correctness checks all loaded bytes through the reduction. It reaches5.1152TB/s (30cold samples).
The scheduled estimate is85.1% of that empirical streaming read rate. This is not proof of full
HBM hardware saturation: access patterns and the counter correction differ from the calibration.
For control_long_0, main padded QK/PV938.182GFLOP plus row-sum58.636GFLOP gives
0.216ms at the dense theoretical matrix ceiling. The estimated3.569GB of reads gives0.698ms
at5.115TB/s. The counter-profiled kernel is0.820ms. The read-rate projection therefore sets a
much tighter simple bound than matrix throughput. It excludes vector issue and synchronization.
The remaining kernel is consistent with a primarily bandwidth-constrained regime for this shape.
Do not multiply all TFLOPS by the padding factor and compare to the wrong sparse/FP4 peak.

Preparation and API
prepare_work_schedule(query_lengths,key_lengths,device,num_ctas=512,block_m=128)
uses known CPU lists and builds a capacitated longest-job-first static permutation.
All work items are independent and remain block-uniform. There is no per-lane scalar backdoor.
The schedule is applied to initial item lookup, the persistent loop and next-item prefetch.
Every workgroup retains its original item count and async synchronization semantics.
The CPU scheduling pass measured0.62..0.85ms before GPU upload in the prototype confirmation.
Plan construction, upload and first-use metadata are excluded from core timing. Reuse is necessary
for an end-to-end benefit. Dynamic GPU-only offsets are not automatically sorted by this API.
The optional schedule is checked against total tokens, batch, device, tile size and grid.
The supplied CPU lengths must match the device offsets exactly; values are not read back to verify.
forward_prequantized(...,work_schedule=schedule) and forward(...,work_schedule=schedule) accept it.
For BF16 forward, an unspecified block_m follows the supplied schedule. Default unscheduled behavior remains.
