Changes
1. prepare_q produces E4M3 [tokens,4,128] and uint8 E8M0 [tokens,4,4].
   It exactly matches fused 32-query-row x 32-feature quantization; groups restart per sequence.
2. forward_prequantized accepts Q8/Q scales and the existing prepared K/V ABI.
   It needs no original BF16 operands; preparation and metadata initialization are outside core timing.
   External row-wise Q scales are supported, including scales that differ for adjacent rows.
3. Move both main-loop async wait_group(0) operations after register-only softmax.
   Every subsequent LDS consumer still follows the full wait. Shared buffer alternation,
   async commit groups, stage barriers, epilogue waits, and iteration boundaries remain.
   This is a valid block-uniform program; no hardware-ID scalars or divergent lane control.
4. Include the previously validated natural-log LSE correction (subtract log2 shift 4).

First-principles roofline
Official dense MXFP8 peak ~4.614 PF/s (not the sparse or MXFP4 peak); retail HBM8TB/s.
This board reports 6.810 TB/s and max GPU2.2GHz, 256CUs, 160KiB LDS/CU.
Local calibration: streaming copy read+write4.484TB/s; resident scaled-MFMA32 ~3.046PF/s,
16x16 scaled MFMA ~3.220PF/s. These are calibration targets, not universal hard bounds.
For BM128: padded main math/requested KV byte = 4*D*128/(2*D+8) = 248.24 FLOP/byte.
Query/key padding matters; rowsum MFMA adds another6.25% to main padded arithmetic.
R = sum(ceil(q_i/128)*ceil(k_i/256)*256).
Main padded FLOPs = 4*H*D*128*R; K/V CTA-request bytes = H*(2*D+8)*R.
Actual HBM bytes can be lower through cache reuse. Softmax/vector issue, LDS and synchronization
are excluded from the simple compute/memory lower bounds and need separate modeling.
Best optimistic latency >= max(matrix-only time, compulsory HBM time); such a bound is not a prediction.
  control_short_1: padding 2.946x; measured 0.1578ms; matrix-only theoretical 0.0247ms; unique-HBM lower 0.0588ms; all-CTA-read HBM projection 0.0696ms.
  control_long_0: padding 2.508x; measured 1.1445ms; matrix-only theoretical 0.2160ms; unique-HBM lower 0.5006ms; all-CTA-read HBM projection 0.5606ms.

HBM counter calibration
Collecting FetchSize+WriteSize in one pass exceeded hardware counter capability and aborted;
the failed profiler process was stopped. FetchSize-only collection succeeded.
FetchSize reported2,147,484,992bytes for a known4,294,967,296byte streaming read.
Its documented gfx950 derived formula under-reports this calibration by almost exactly2x.
Attention raw FetchSize1,805,775,040bytes over1.116873ms; empirically corrected estimate
'3.612GB and 3.234TB/s'.
The correction is local empirical calibration, not a validated universal ROCm metric fix.
Conclusion: core is constrained by memory/issue overlap and vector softmax as well as matrix work.
Pure matrix-compute saturation and full-board HBM bandwidth saturation are not established.
The improved schedule demonstrates an avoidable exposed-memory-wait component.

Other hypotheses
Q prequantization alone: ~3.3% long gain, neutral/slightly worse short; fused Q work overlaps prefetch.
Scheduler-group options2/4/8 slower; softmax priority1 small mixed benefit, not accepted.
Earlier copy and skipping last persistent prefetch small mixed gains, not accepted.
BM64 slower despite reduced padded math: loses arithmetic intensity and adds K/V requests.
Grid256 slower; grid1024 mixed and regresses candidate_long_3, not accepted.
BM256 changes floating-point rounding across tile shapes, failed strict bitwise screening;
not retained or classified as a numerical bug. BM256 prequant regression against its fused path passes.

Next high-value directions
1. Reduce softmax packed-vector instructions and live values without changing the quantization recipe.
2. Improve prefetch distance/buffering only after checking physical buffer aliasing, async completion
   and LDS/register occupancy. Two blocks/CU already use substantial LDS and VGPR resources.
3. Reduce query padding through row-aware tiling while retaining K/V reuse; BM64 alone loses.
4. Keep producer-native MXFP8 K/V as an integration target; attention-only gains do not erase
   full-BF16 K/V conversion/transpose cost.
